================================================================================

Q: Tell us about your project in 30 seconds.
A: "Our solution is a Government-Grade NAWI (Non-Automatic Weighing Instruments) Type 
   Evaluation and Standardized Test Report Generator built for the Department of Consumer 
   Affairs and NPL/RRSL laboratories under SIH Problem Statement 26035.

2. SECTION A: GENERAL PRESENTATION, DOMAIN & BUSINESS QUESTIONS (PPT ROUND)
================================================================================

Q1: What exact problem are you solving?
Ans: Currently, Legal Metrology Officers and RRSL/NPL scientists manually calculate 
     maximum permissible errors (MPE) for weighing balances and commercial scales using 
     paper forms or unstandardized Excel sheets. This is prone to human mathematical 
     error, lacks centralized auditability, and leads to delays in official type evaluation 
     approval. Our platform digitizes and standardizes this entire process end-to-end.

Q2: Which international/national standards does your project comply with?
Ans: It complies strictly with:
     1. OIML R 76-1:2006 (Non-automatic weighing instruments - Metrological requirements & tests).
     2. OIML R 76-2 (Standardized Test Report Format).
     3. Indian Legal Metrology (General) Rules.

Q3: How does your solution benefit the Government/Ministry?
Ans: 
     - 100% Accuracy: Math engine automates MPE evaluation based on Accuracy Classes (Class I, II, III, IIII).
     - Standardized Reports: Uniform official PDF certificates and editable Word DOCX reports.
     - Security & Auditability: OAuth2 JWT Auth with Role-Based Access Control (RBAC) and non-deletable audit trails.
     - Faster Processing: Reduces report generation time from hours to seconds.

Q4: Who are the target users of this system?
Ans: We have 4 distinct roles configured in our Role-Based Access Control (RBAC):
     1. Admin: System setup, user management, laboratory configuration.
     2. Lab Technician: Inputs raw test observations (Span, Eccentricity, Repeatability, etc.).
     3. Reviewer / Senior Metrology Officer: Reviews evaluation results and approves/rejects sessions.
     4. Viewer: Read-only access for external auditors or departmental monitoring.

Q5: What makes your project stand out from a basic CRUD or Excel sheet?
Ans: Excel sheets lack role authentication, tamper protection, workflow enforcement, and automated database archiving. 
     Our system features:
     - Automated OIML evaluation math engine.
     - Structured multi-step wizard for field testing.
     - Role-based approval workflow (Draft -> Under Review -> Approved).
     - On-the-fly binary document synthesis (ReportLab PDF + python-docx).
     - Enterprise security with JWT tokens & database audit trails.

Q6: How does this system scale across multiple state RRSL labs across India?
Ans: The system is designed with multi-tenancy in mind. Each user account is assigned a `lab_code` (e.g. `RRSL_BANGALORE`, `NPL_DELHI`). 
     Data is partitioned by laboratory, while central administrators can view nationwide metrics and compliance reports across all labs in a unified dashboard.

Q7: What is your rollout strategy for government adoption?
Ans: 
     Phase 1: Pilot testing at 5 Regional Reference Standard Laboratories (RRSLs).
     Phase 2: Training Legal Metrology Officers and integrating with state portal databases.
     Phase 3: Nationwide rollout with cloud deployment on NIC (National Informatics Centre) infrastructure or MeghRaj Cloud.

3. SECTION B: PROTOTYPE DEMONSTRATION & LIVE WORKFLOW QUESTIONS (DEMO ROUND)
================================================================================

Q1: Walk us through the live demo workflow.
Ans: 
     1. Login as Lab Technician using JWT credentials.
     2. Register/Select a Manufacturer & Instrument specifications (Class, Max Cap, min cap, e value).
     3. Create a Test Session (Generates unique code e.g. NAWI-20260824-X1Y2).
     4. Enter Test Observations in Wizard:
        - Weighing Performance & Linearity (Increasing/Decreasing loads).
        - Eccentricity Test (5 platform positions).
        - Repeatability Test (3+ identical weighings).
        - Discrimination & Overload Check (> Max + 9e).
     5. Automatic Evaluation: The system evaluates every reading against OIML Table 6 MPE rules and tags Pass/Fail.
     6. Submit for Review: Session moves to UNDER_REVIEW status.
     7. Login as Reviewer: Inspect observations and click APPROVE.
     8. Export: Download tamper-proof PDF certificate or editable DOCX.

Q2: What happens if a technician enters an invalid reading or invalid data?
Ans: We have dual-layer validation:
     - Frontend Validation: Form inputs have strict TypeScript interfaces, HTML5 min/max bounds, and numeric validation to prevent empty or negative values.
     - Backend Validation: FastAPI Pydantic v2 schemas reject malformed payloads with 422 Unprocessable Entity errors before hitting the database.

Q3: How does the system evaluate PASS or FAIL status?
Ans: The backend OIML Math Engine (`oiml_engine.py`) takes the instrument's Accuracy Class (Class I, II, III, or IIII) and scale interval `e`. 
     It calculates load in terms of `m/e`, checks the exact MPE tier (e.g. ±0.5e, ±1.0e, ±1.5e), calculates Indication Error `E = Indication - Load`, 
     and checks if `|E| <= MPE`. If all tests pass, the session overall status is set to PASS.

Q4: Can an approved test report be modified by a technician?
Ans: No. Once a session status transitions to "APPROVED", the system locks editing for Lab Technicians. Any modifications require an Admin override, 
     and every action is recorded in the `audit_logs` database table.

Q5: What happens if a technician leaves a session halfway through?
Ans: Sessions can be saved in "DRAFT" or "IN_PROGRESS" status. Technicians can close their browser, log back in later from any machine, 
     and resume their test session right from where they left off without losing raw observation data.

Q6: Can historical test reports be downloaded anytime later?
Ans: Yes. All completed sessions and their evaluation payloads are permanently stored in the database. Reviewers or Admins can perform 
     historical lookups by Manufacturer, Serial Number, Session Code, or Date Range and instantly re-generate PDF or DOCX reports on demand.

4. SECTION C: FRONTEND TECHNICAL Q&A (SEPARATE FRONTEND DEEP-DIVE)
================================================================================

Q1: What is your Frontend Tech Stack and why did you choose it?
Ans: 
     - React 18 (TypeScript): Component-based UI, type safety, predictable state management.
     - Vite 5: Extremely fast build tool with instant HMR (Hot Module Replacement) and ESbuild module bundling.
     - Tailwind CSS 3.4 + Vanilla CSS: Modern, responsive glassmorphic UI design system with consistent styling tokens.
     - Recharts: Modular React charting library for analytics dashboards (Pie charts for session statuses, Bar charts for accuracy class distribution).
     - Axios: Promised-based HTTP client for REST API calls with interceptors for auth tokens.
     - Lucide React: Clean, modern vector icon set tailored for administrative & lab portals.

Q2: How do you manage global state and authentication token in Frontend?
Ans: We store the JWT Bearer token securely in `localStorage` upon login. We use Axios request interceptors to automatically attach 
     `Authorization: Bearer <token>` to every outgoing HTTP API request. If an API returns a 401 Unauthorized response, an interceptor catches 
     it and redirects the user to the Login page.

Q3: How is the multi-step Test Wizard built in React?
Ans: The Test Wizard is built using modular step components managed by a central state hook (`currentStep`). 
     Step-specific data is kept in state until final submission. Form inputs are validated in real-time before enabling the "Next Step" button.

Q4: How did you optimize Frontend performance?
Ans: 
     - Vite code-splitting and dynamic imports.
     - Functional components with React Hooks (`useState`, `useEffect`, `useCallback`, `useMemo`) to prevent unnecessary re-renders.
     - Tree-shaking unused icons from Lucide-React and charting utilities from Recharts.
     - CSS animation hardware acceleration for smooth transition effects.

Q5: How do you handle UI responsiveness across screens (Laptops, Tablets, Mobile)?
Ans: Using CSS Flexbox, CSS Grid, and Tailwind responsive breakpoints (`sm:`, `md:`, `lg:`, `xl:`). The sidebar converts into a collapsible drawer 
     on smaller screens, and data tables use horizontal scroll wrappers to prevent layout breaking.

Q6: How do you render graphs and visual data on the Dashboard?
Ans: We pass structured API analytics data into Recharts `<ResponsiveContainer>`, `<PieChart>`, `<Pie>`, `<BarChart>`, and `<Bar>` components. 
     Tooltips and custom legends are styled using Tailwind CSS tokens to match the dark/light glassmorphism theme.

Q7: Why did you use Vanilla CSS + Tailwind CSS instead of third-party UI libraries like MUI or AntD?
Ans: Heavy UI libraries like MUI or Ant Design introduce massive bundle overhead, rigid default themes, and styling performance costs. 
     Using Tailwind CSS with custom Vanilla CSS CSS-variables allowed us to craft a custom, lightweight, high-performance glassmorphic UI 
     tailored specifically to Indian Government portal design guidelines.

Q8: How do you handle binary file downloads (PDF/DOCX) on the Frontend?
Ans: Axios is configured with `responseType: 'blob'`. When the backend returns binary document bytes, frontend creates a temporary Object URL 
     via `window.URL.createObjectURL(new Blob([response.data]))`, attaches it to a hidden `<a>` DOM element with a `download` attribute, triggers 
     a click event programmatically, and cleans up the Object URL using `window.URL.revokeObjectURL()`.

Q9: How do you handle network latency, loading states, and API error toasts?
Ans: Every async API interaction sets a component `loading` boolean state to render animated spinner buttons or skeleton screen placeholders. 
     API errors are caught in Axios catch blocks and displayed using user-friendly banner/toast alerts displaying exact backend error messages.

5. SECTION D: BACKEND TECHNICAL Q&A (SEPARATE BACKEND DEEP-DIVE)
================================================================================

Q1: What is your Backend Tech Stack and why did you choose it?
Ans: 
     - Python 3.13: Modern Python with speed improvements and enhanced type annotations.
     - FastAPI: Asynchronous, high-performance web framework based on OpenAPI standards. Fast performance comparable to NodeJS and Go.
     - Pydantic v2: Rust-backed ultra-fast data validation and schema parsing.
     - SQLAlchemy: Powerful SQL ORM with full relational integrity and object mapping.
     - Alembic: Schema migration tool for smooth database updates.
     - Uvicorn: Lightning-fast ASGI (Asynchronous Server Gateway Interface) server.

Q2: What is your Database architecture?
Ans: 
     - Development/Demo: SQLite (`nawi_test.db`), zero-configuration, lightweight for local demo.
     - Production Deployment: PostgreSQL 15+ (seamless migration via SQLAlchemy dialect switch in `.env`).
     - Core Database Tables:
       1. `users` (id, username, email, hashed_password, role, lab_code)
       2. `manufacturers` (id, name, code, license_number, country)
       3. `instruments` (id, manufacturer_id, model_name, serial_number, accuracy_class, max_capacity, min_capacity, e_interval)
       4. `test_sessions` (id, session_code, instrument_id, technician_id, reviewer_id, status, overall_pass)
       5. `test_observations` (id, session_id, test_type, raw_data_json, evaluated_data_json, is_passed)
       6. `audit_logs` (id, user_id, action, resource, timestamp, ip_address)

Q3: How does the automated Document Generation (PDF & DOCX) work under the hood?
Ans: 
     - PDF Generation: Uses `ReportLab 4.x`. When requested, FastAPI queries session data from the database, builds a `SimpleDocTemplate` in memory using `io.BytesIO()`, formats headers, tables, MPE status badges, signature fields, and streams the binary PDF back to the frontend with `StreamingResponse` header `application/pdf`.
     - DOCX Generation: Uses `python-docx`. Constructs structured Microsoft Word document tables and paragraphs dynamically, allowing legal metrology officers to download an editable copy if manual annotations are required.

Q4: How do you secure password storage and authentication?
Ans: 
     - Passwords are never stored in plain text. We hash passwords using `Passlib` with the `Bcrypt` algorithm.
     - Authentication uses OAuth2 with Password Flow. Upon verification, FastAPI issues a signed JSON Web Token (JWT) using `python-jose` with `HS256` signature algorithm and an expiration timestamp (`exp`).

Q5: How is Role-Based Access Control (RBAC) enforced in FastAPI?
Ans: We use FastAPI's Dependency Injection (`Depends()`). We created custom dependency functions (e.g. `get_current_active_user`, `require_role(["ADMIN", "REVIEWER"])`) in `app/core/deps.py`. If a user with role `LAB_TECHNICIAN` tries to hit an approval endpoint, FastAPI raises HTTP 403 Forbidden automatically.

Q6: How do you maintain Audit Logs?
Ans: Every critical mutation (creating session, updating observation, changing session status, deleting records) invokes an audit helper function that writes an entry into `audit_logs` with `user_id`, `action`, `resource`, `details_json`, `ip_address`, and ISO timestamp.

Q7: How do you handle Cross-Origin Resource Sharing (CORS) between React and FastAPI?
Ans: In FastAPI main file, we register `CORSMiddleware` with explicit `allow_origins` set to frontend origin `http://localhost:5173`, allowing `allow_credentials=True`, `allow_methods=["*"]`, and `allow_headers=["*"]`.

Q8: How do you handle schema migrations when database requirements change?
Ans: We use `Alembic`. When models in SQLAlchemy are updated, running `alembic revision --autogenerate -m "description"` detects class changes 
     and generates structured migration scripts. `alembic upgrade head` applies migrations seamlessly without dropping existing tables or data.

Q9: How do you prevent SQL Injection and ORM performance bottlenecks?
Ans: 
     - SQL Injection Prevention: SQLAlchemy ORM automatically parameterized all query values, neutralizing raw SQL injection attacks.
     - Performance: We use indexed foreign keys and explicit eager loading (`joinedload` / `selectinload`) to prevent N+1 query performance degradation when querying instruments with observations and user details.

6. SECTION E: TRICKY / CURVEBALL & ADVANCED DEPLOYMENT QUESTIONS
================================================================================

Q1: "Why FastAPI instead of Django or Node.js/Express?"
Ans: 
     - Over Django: Django is monolithic and heavier. FastAPI is lightweight, async native, auto-generates OpenAPI / Swagger docs (`/docs`), and handles asynchronous document generation without blocking.
     - Over Node.js: Python is the de facto standard for scientific computing, mathematical analysis, and libraries like `ReportLab` and `python-docx` for document generation.

Q2: "Why React SPA instead of Next.js Server-Side Rendering (SSR)?"
Ans: Our app is an internal, secure, authentication-gated laboratory portal behind RBAC logins. It does not require public Search Engine Optimization (SEO). 
     A React Single Page Application (SPA) bundled via Vite provides instant user interactions, zero server-rendering latency for dashboard widgets, 
     and simple static asset deployment on Nginx/S3.

Q3: "What if the internet fails in a remote field testing laboratory?"
Ans: Our architecture allows local offline deployment. Because the backend runs on Uvicorn with SQLite/PostgreSQL locally, the entire application can be hosted on a local lab server or portable laptop without requiring active internet connectivity. Reports can be generated locally.

Q4: "How do you handle future changes in OIML regulations?"
Ans: Our math engine (`oiml_engine.py`) is decoupled from the API routers and database models. The MPE limits and formulas are defined in config dictionaries. If OIML updates its table limits, we only need to update the configuration module without rewriting database schemas or frontend code.

Q5: "How do you prevent certificate forgery or tampering?"
Ans: 
     1. Generated PDF certificates contain a unique cryptographic hash fingerprint / session code.
     2. PDF metadata locks editing.
     3. Every certificate generation event is logged in the audit trail database.
     4. Future roadmap: Integration of QR code verification link linked to government portal database.

Q6: "How do you containerize and deploy this project in production?"
Ans: We use Docker and Docker Compose (`docker-compose.yml`).
     - `frontend`: Containerized Node/Vite build served via lightweight Nginx web server.
     - `backend`: Containerized Python 3.13 FastAPI app running on Uvicorn ASGI server with Gunicorn workers.
     - `db`: Production PostgreSQL 15 database container with persistent data volumes.
     - Nginx acts as a reverse proxy handling SSL termination and proxying `/api` requests to backend containers.

Q7: "What automated testing strategy did you follow?"
Ans: We use `pytest` for backend API integration tests and math engine unit tests (`tests/test_oiml.py`). We test edge cases in scale interval calculations (`m/e` boundaries), JWT token authentication routes, and role permission checks.

Q8: "How do you handle concurrent users or multiple technicians submitting test reports simultaneously?"
Ans: FastAPI is built on ASGI (`uvicorn` / `asyncio`), allowing non-blocking I/O operations. Database connections are managed via SQLAlchemy connection pooling with connection timeouts and transaction isolation levels, ensuring high concurrency without data race conditions.

Q9: "What was the biggest technical challenge you faced while building this?"
Ans: "The biggest challenge was correctly implementing OIML R 76-1 Table 6 MPE calculations for 4 different Accuracy Classes (Class I, II, III, IIII) across variable scale intervals (`e` and `d`), and converting those mathematical results dynamically into tamper-proof ReportLab PDF tables in real-time."

Q10: "If you had 2 more weeks, what feature would you add next?"
Ans: 
     1. Digital Certificate Signing: Integrating Aadhar eSign / X.509 Digital Signature Certificates (DSC) into PDFs.
     2. QR Verification Portal: Public scanner page where anyone can scan the PDF QR code to verify report authenticity.
     3. AI Anomaly Detection: Flagging suspicious load readings that deviate significantly from expected load cell linearity.
